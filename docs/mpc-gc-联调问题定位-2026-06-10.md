## 一、结论

当前 `MPC=GC` 联调已经确认：

- 我方 `3000` 后端中间层链路正常
- 对方 `8080` Flask task 分发层可正常创建任务、接收卖方数据、触发计算
- 对方 `8091` Go MPC 服务可正常响应健康检查
- 实际失败点发生在对方 `8091` 的 GC 评估逻辑内部

本次失败不是前端/我方后端接口格式问题，核心报错为：

```text
混淆电路评估失败: 输出标签无法识别
```

从源码看，这个问题大概率是对方 GC 实现本身的标签传播/AND 门 garble 逻辑存在缺陷。

## 五、源码定位

### 1. 直接报错位置

报错 `"输出标签无法识别"` 出现在：

- `app/service/mpc/crypto/garbledcircuit/evaluator.go`

相关逻辑：

```go
outputValue, err := ParseOutputBool(outputLabel, gc)
if err != nil {
    return nil, err
}
```

`ParseOutputBool()` 内部：

```go
if labelsEqual(outputLabel, outputLabelMap[false]) {
    return false, nil
} else if labelsEqual(outputLabel, outputLabelMap[true]) {
    return true, nil
}

return false, fmt.Errorf("输出标签无法识别")
```

这说明：

- 电路评估已经跑完
- 但最终得到的 `outputLabel` 既不等于 Garbler 保存的 `false` 输出标签，也不等于 `true` 输出标签

### 2. 调用链

调用链如下：

1. `app/service/mpc/server/handlers/garbled_circuit.go`
   - `EvaluateGC()`
2. `evaluator.EvaluateWithStats(...)`
3. `ParseOutputBool(outputLabel, gc)`
4. 抛出：
   - `输出标签无法识别`

## 六、最可疑的实现问题

### 问题点 1：Garbler 在 AND 门混淆时使用了不完整的实际输入值

在：

- `app/service/mpc/crypto/garbledcircuit/garbler.go`

代码：

```go
pa := false
pb := false
if gate.InputA < len(inputsA) {
    pa = inputsA[gate.InputA]
}
if gate.InputB < len(inputsA) {
    pb = inputsA[gate.InputB]
}

table, cLabels, err := g.hg.GarbleANDGate(aLabels, bLabels, pa, pb)
```

这里的 `inputsA` 只包含 A 方原始输入位。

但电路中的 AND 门输入并不总是原始 A 方输入，还会包含：

- B 方输入位
- 中间门输出位
- 常量门结果

对于这些情况：

- `gate.InputA` 或 `gate.InputB` 通常不在 `inputsA` 范围内
- `pa` / `pb` 会默认保留为 `false`

这意味着：

- 大量 AND 门在 garble 阶段使用了错误的 `pa/pb`

### 问题点 2：`GarbleANDGate()` 真正依赖 `pa/pb`

在：

- `app/service/mpc/crypto/garbledcircuit/halfgates.go`

`GarbleANDGate()` 内部明确使用了 `pa/pb`：

```go
if pa {
    bDelta := xorWireLabel(bLabels[1], bLabels[0])
    tg = xorBytes16(tg, bDelta.Value)
}

if pb {
    aDelta := xorWireLabel(aLabels[1], aLabels[0])
    te = xorBytes16(te, aDelta.Value)
}
```

如果这里用错 `pa/pb`，就可能导致：

- Garbler 侧生成的混淆表与 Evaluator 侧标签传播不一致
- 电路虽然能评估结束
- 但最终输出标签不再落在 Garbler 原先记录的输出标签对中

这与当前现象完全一致。

## 七、为什么更像底层 GC bug，而不是接口问题

如果是接口层问题，通常更可能出现：

- 参数校验失败
- 缺字段
- JSON 解析失败
- 任务不存在
- 授权失败

但当前现象不是这些，而是：

- 任务正常创建
- 授权正常生成
- `evaluate` 已进入核心评估
- 最后在输出标签解释阶段失败

这更像：

- GC 协议实现不自洽
- 标签映射/门语义/half-gates 实现存在内部错误

## 八、建议对方优先排查的点

建议优先检查以下几点：

1. `garbler.go` 中 AND 门 garble 时，为什么用 `inputsA` 推导 `pa/pb`。
2. `pa/pb` 是否本来就不应该依赖门输入的“实际值”。
3. 如果协议设计确实需要 `pa/pb`，那么中间门和 B 方输入门的真实值从哪里来。
4. `NOT` / `XOR` / `BUF` 门传播后的输出标签，是否一定还能和 `OutputLabels` 对齐。
5. 是否能写一个最小单测，直接对 `NewLoanEvaluationCircuit()` 做：
   - Garble
   - Evaluate
   - ParseOutputBool
   看纯本地是否能稳定复现 `"输出标签无法识别"`。
