# FL `join` 失败问题说明

日期：2026-06-01

## 一、结论

我们这边 FL 对接链路目前已经确认：

- 创建 FL 合同可以成功
- PCP 能正常返回 `contract_id`
- 卖方 `join` 阶段失败
- 失败点不在我们 buyer/seller 的请求格式
- 失败点在 PCP 内部 `sgx_runtime` 的 FL runtime

也就是说，当前阻塞点是对方 PCP 运行环境问题，不是我们这边前后端参数拼装问题。

## 四、PCP 后端日志结论

PCP backend 日志里，`join` 的报错位置非常明确：

```text
POST /fl/FL_TASK_F14BC2C3E09D4FE9/join HTTP/1.1" 500 Internal Server Error
...
File "/app/app/api/fl/service.py", line 90, in build_join_response
    materials_resp = await client.get(f"{sgx_runtime_url}/materials/fl")
...
httpx.RemoteProtocolError: Server disconnected without sending a response.
```

这说明 PCP 在执行 FL `join` 时，失败发生在：

- `build_join_response()`
- 调用 `GET http://sgx_runtime:50051/materials/fl` 这一步

也就是说，问题发生时甚至还没有走到：

- `/compute/fl/rewrap-bottom-model`

所以目前不是 bottom model 重包失败，而是连 FL materials 都拿不到。

## 五、SGX runtime 日志结论

`sgx_runtime` 容器日志里反复出现：

```text
OpenBLAS error: Memory allocation still failed after 10 retries, giving up.
```

同时日志中还能看到 runtime 反复重新启动：

```text
[sgx] Starting SGX runtime on port 50051
INFO:     Started server process [2]
...
OpenBLAS error: Memory allocation still failed after 10 retries, giving up.
```

这说明当前 FL runtime 在运行过程中触发了内部崩溃或异常退出，然后被重新拉起。

## 六、源码定位

相关 PCP 源码位置如下：

- `/home/super/tr/pcp/app/api/fl/router.py`
- `/home/super/tr/pcp/app/api/fl/service.py`
- `/home/super/tr/pcp/app/sgx_runtime/server.py`
- `/home/super/tr/pcp/app/compute/fl_runner.py`

调用链路为：

1. `app/api/fl/router.py`
   - `join_task()`
2. `app/api/fl/service.py`
   - `build_join_response()`
3. `build_join_response()` 内部先调用：
   - `GET /materials/fl`
4. 之后才会调用：
   - `POST /compute/fl/rewrap-bottom-model`
5. `app/sgx_runtime/server.py` 中的 `/materials/fl`
   - 会进入 FL runtime 逻辑
6. `app/compute/fl_runner.py`
   - 顶层直接 import `torch`

目前从现象上看，问题大概率发生在：

- `materials/fl` 路径对应的 FL runtime 初始化/import 阶段

而不是我们传入的 seller 公钥、bottom model 包、seller zip 包格式有问题。

## 七、当前环境补充信息

PCP 当前配置中，FL trusted runtime 的地址是：

- host：`sgx_runtime`
- port：`50051`

配置来自 `config.yml`：

```yaml
compute:
  sgx:
    rpc_scheme: "http"
    rpc_host: "sgx_runtime"
    rpc_port: 50051
```

容器状态观察结果：

- `pcp_backend`：健康
- `pcp_sgx_runtime`：`/health` 看起来健康

但是：

- `health` 正常不代表 FL runtime 正常
- 实际调用 `materials/fl` 时仍然会断连并触发异常

## 八、我们这边已确认排除的方向

以下方向目前已经基本排除：

- buyer 上传 `top.pt` / `bottom.pt` 的接口字段格式错误
- seller 上传公钥的字段格式错误
- seller 上传 `seller_fl_batch.zip` 的接口字段格式错误
- 我们自己定义了错误的 `batch_index`

另外，我们这边已经把业务流程收束成单轮 FL：

- `max_epochs = 1`
- `batch_index = 0`

所以当前问题和多轮训练设计也没有关系。

## 九、建议对方优先排查的点

建议 PCP 团队优先检查：

1. 为什么 `GET /materials/fl` 会在 `sgx_runtime` 内部直接断开连接。
2. `Occlum/SGX` 运行环境里，`torch` 或 `OpenBLAS` 是否存在内存限制问题。
3. 是否需要限制 BLAS 线程数，或者调整相关内存配置。
4. 当前这套 `sgx_runtime` 镜像是否真正支持 FL runtime，而不是只支持 PRE。
5. 修复 `materials/fl` 后，再继续验证：
   - `join`
   - `/compute/fl/rewrap-bottom-model`
